# 조회 요청 개선 1차 — 2026-11-12

## 적용 범위

- 업무보드: 열 구성·체크 상태·연결 원본의 업무 조회 결과를 같은 화면 로딩 안에서 공유한다. 열 구성을 위한 전체 목록도 공유한다. 실패는 재시도 가능하다.
- 공유 데이터는 전역 캐시가 아니다. 계정 토큰, 월, 목록 응답, 저장 후 갱신, 상세 진입/복귀가 바뀌면 새로 조회한다.
- 메일: 필터와 페이지의 목록 effect를 통합한다. 필터 변경 시 1페이지로 돌아가며, 이전 응답 차단은 유지한다.
- 거래처 상세: 계약 조회에 company_id를 전달한다. 서버는 기존 client_id 범위 안에서 추가 필터링한다.
- 기장 계약 목록: 계약 응답에 company_category를 추가하고, 구분 표시만을 위해 거래처 전체를 별도 순회하던 요청을 제거한다.
- 블로그 목록·기장 현황: 늦게 도착한 이전 조건의 응답이 새 화면을 덮어쓰지 않도록 한다.

## 배포

SQL 적용 없음. 테이블·컬럼·저장 데이터 변경 없음.
1. 서버를 먼저 배포한다. 기존 계약 목록 API에 선택 company_id 필터와 company_category 응답을 추가했다. 기존 호출도 그대로 지원한다.
2. 어드민 프론트를 배포한다. 로컬 프론트는 새로고침한다.
3. 회사별 계약 목록, 계약 수정/메모, 업무 완료 체크, 월 이동, 메일 필터/페이지, 블로그 검색을 확인한다.

프론트만 먼저 배포하면 구 서버의 계약 응답에 company_category가 없어 계약 목록의 법인/개인 구분이 '-'로 표시될 수 있다.

## 검증과 한계

TypeScript 검사 및 요청 공유/계약 편집/업무 요약 테스트 수행.
요청 공유 테스트의 100개 보드 × 3개 소비자: 300 -> 100회. 이는 재현 테스트이며 실제 화면 전체 HTTP 요청 수나 운영 응답시간 감소율이 아니다.
기장 계약 목록의 별도 거래처 조회는 거래처 수 N에 대해 ceil(N/100)회에서 0회로 줄어든다.
서버 파일 구문 검사는 통과했다. 로컬 Python에 SQLAlchemy가 없어 서버 통합 테스트는 실행하지 못했다.
운영 DB나 로그인된 브라우저를 통한 실제 응답시간은 측정하지 않았다.

배포 전후 동일 계정·귀속월·전체보기·거래처 수로 Network 기록을 비교해야 한다. 최초 개발 서버 컴파일을 제외하고 각 월 왕복을 5회 측정한다. 전체 요청 수, /items 중복 수, 마지막 체크 상태 표시 시점, 서버 응답 p50/p95를 기록한다. Network 기록 공유 시 인증 헤더·쿠키는 제거한다.
